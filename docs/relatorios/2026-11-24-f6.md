# Relatório F6 — Posições/Carteira (24/11/2026)

## Veredito

**Implementação validada; aceitação do dono pendente.** A F6 não é marcada completa porque falta a
reconciliação manual de **duas posições reais com o extrato da corretora**. Nenhuma reconciliação foi
inventada. F7 e F8 não foram iniciadas.

## Arquitetura entregue

- Journal operacional em **PostgreSQL + SQLAlchemy Core + Alembic**; lago analítico continua
  Parquet/DuckDB e `model_version` continua 2.
- Migration inicial única `0001_f6_initial`: `position`, `position_leg`, `position_event`, `prediction`,
  índices únicos parciais de um `open`/um `close` e triggers de `UPDATE`/`DELETE`/`TRUNCATE`.
- Volume nomeado `b3o-postgres`, sem porta publicada, montado em `/var/lib/postgresql` (PostgreSQL 19.0).
  `app`/`dev` aplicam Alembic antes do uvicorn; GET não cria schema.
- Abertura idempotente por `client_position_id`; fechamento transacional com `SELECT ... FOR UPDATE`.
  Detalhe fechado lê o snapshot completo do evento `close`.
- API/MCP compartilham o mesmo `QueryService`. A tool é somente `positions`, read-only, com paginação.

## Correções de revisão incorporadas

- `max_rows=0` rejeitado; `offset`/`next_offset` funcionam na API e no MCP.
- Token validado antes do parse JSON; token não ASCII → 401; corpo limitado em 64 KiB.
- Marca zero/negativa/não finita não vira preço; fechamento sem marca positiva é bloqueado.
- `evaluate_on` precisa ser sessão do calendário e coerente com o horizonte.
- `event_in_window` não usa evento posterior à consulta histórica.
- Payoff usa strike vigente; truncamento omite a curva em vez de mostrar parcial.
- Rota de detalhe não aninhada; service worker de posições é `NetworkOnly`.
- Rascunho + UUID persistem em `sessionStorage` até sucesso/descarte; token não fica no rascunho.
- Tabelas horizontais têm região focável; foco do diálogo e 401/409 tratados.

## Pendências

1. **Dono:** reconciliar P&L de duas posições reais com a corretora.
2. **Backup:** destino/automação de `pg_dump` ainda não escolhidos; volume não é backup.
3. O papel PostgreSQL do runtime é o dono do banco. Triggers protegem o caminho normal, mas um
   superusuário pode contorná-los; separar papel runtime é endurecimento futuro, não bloqueio do uso pessoal.
