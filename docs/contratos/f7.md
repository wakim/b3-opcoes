# Contrato F7 — Diário e calibração pessoal

## 1. Escopo e arquitetura

- O Diário registra decisões que **não criam posição** e mede a calibração das previsões
  estruturadas do dono. O produto continua descritivo: não há classe de sinal, ranking, taxa do
  backtest F1b ou recomendação (ADR-023/024).
- Persistência em **PostgreSQL + SQLAlchemy Core + Alembic**, separada do lago Parquet/DuckDB.
  A migration F6 `0001_f6_initial` não é editada; a evolução é `0002_f7_journal` +
  `0003_f7_prediction_parent` (esta última torna `prediction.position_id` nullable).
- Toda leitura do lago passa pela `QueryService`. O frontend apenas formata números do backend.
- `model_version` continua **2**; nenhuma fórmula de `metrics/`, `ingest/` ou `store/` muda.

## 2. Modelo append-only

### `decision`

Evento de decisão, com:

```text
id, underlying, session, decision_type, context, notes,
position_id NULL, client_decision_id NULL, request_fingerprint NULL, created_at
```

- `decision_type`: `no_entry | entry | exit | hold | watch | other`.
- Limites: ticker 32 caracteres; contexto 500; notas 4.000; UUID4.
- `position_id` é opcional e único. A abertura de uma posição pela Carteira espelha um evento
  `entry` com `context = position_open`; o `POST /api/journal` nunca cria posição.
- `client_decision_id` é único. Mesmo UUID + mesmo corpo devolve a decisão existente; corpo
  diferente → `409 decision_id_conflict`.

### `prediction`

A linha F6 continua sendo a semente imutável. A F7 torna `position_id` nullable e acrescenta
`decision_id`, com `CHECK` de que exatamente um dos dois pais existe. O índice parcial garante no
máximo uma previsão por decisão; o índice único F6 continua garantindo no máximo uma por posição.

As colunas legadas `status`/`observed` permanecem `pending`/`null` e **nunca são atualizadas**.

### `prediction_evaluation`

Evento append-only com:

```text
id, prediction_id, session, observed NULL, status, void_reason NULL,
source, model_version, created_at
```

- `status`: `hit | miss | void`.
- `hit`/`miss` exigem `observed` não nulo e sem `void_reason`.
- `void` exige `observed` nulo e `void_reason` não nulo.
- Índice único `(prediction_id, session)` impede duplicação. O lote também usa lock na previsão.
- O estado atual é o evento mais recente por `(session, created_at, id)`, derivado na leitura.

Triggers bloqueiam `UPDATE`, `DELETE` e `TRUNCATE` nas seis tabelas do journal. GET não cria schema;
Alembic é o único caminho de criação/evolução.

## 3. Autenticação e limites

- Leitura de `/api/journal*` é liberada na tailnet.
- `POST /api/journal` exige `X-App-Token`; a dependência roda antes do parse JSON.
- Token ausente no servidor → `503 app_token_missing`; ausente/inválido no cliente → `401`.
- Corpo máximo: 64 KiB. Inteiros acima do int64 e números não finitos → `400`.
- Listas: no máximo 60 linhas; resposta: no máximo 200 KB, com truncamento honesto.
- `max_rows` aceita 1…60 (default 20). `max_rows=0` → `400`. `offset` é inteiro não negativo
  dentro do int64. `meta.total/offset/next_offset` navegam o recorte inteiro.

## 4. API HTTP

Envelope canônico `{as_of_session, model_version, data, meta}`.

### `POST /api/journal`

```json
{
  "client_decision_id": "uuid4-estável-no-rascunho",
  "underlying": "PETR4",
  "date": "2026-11-18",
  "decision_type": "no_entry",
  "context": "esperando resultado",
  "notes": "não entrei antes do resultado",
  "prediction": {
    "metric": "spot",
    "operator": ">=",
    "value": 41.30,
    "horizon_sessions": 1,
    "evaluate_on": "2026-11-19"
  }
}
```

- `date` é opcional (default última sessão do lake) e precisa ser sessão real.
- `underlying` precisa existir como `010`/`020` na sessão; ticker de opção não é aceito.
- `prediction` é opcional. Notas/texto livre nunca são convertidos em previsão.
- Retorna `{decision: ...}` no mesmo formato do detalhe.

### `GET /api/journal?date=&max_rows=&offset=`

`data.decisions` em ordem de sessão DESC, `created_at` DESC e id. Cada decisão traz:

```json
{
  "id": "uuid",
  "underlying": "PETR4",
  "session": "2026-11-18",
  "decision_type": "no_entry",
  "context": "esperando resultado",
  "notes": "não entrei antes do resultado",
  "position_id": null,
  "created_at": "2026-11-24T...-03:00",
  "prediction": {
    "id": "uuid",
    "metric": "spot",
    "operator": ">=",
    "value": 41.3,
    "unit": "brl",
    "horizon_sessions": 1,
    "evaluate_on": "2026-11-19",
    "status": "hit",
    "observed": 41.3,
    "evaluated_on": "2026-11-23",
    "void_reason": null,
    "source": "metrics_underlying",
    "model_version": "2"
  }
}
```

### `GET /api/journal/{id}`

Devolve `{decision: ...}`. UUID inválido → `400`; inexistente → `404 decision_not_found`.

### `GET /api/journal/calibration?max_rows=&offset=`

Agrega **todas** as previsões avaliadas, de decisões ou posições, por métrica + horizonte:

```json
{
  "groups": [{
    "metric": "spot",
    "unit": "brl",
    "horizon_sessions": 1,
    "n": 4,
    "hit": 3,
    "miss": 1,
    "void": 0,
    "hit_rate_pct": 75.0,
    "void_reasons": []
  }],
  "totals": {"n": 5, "hit": 3, "miss": 1, "void": 1, "hit_rate_pct": 75.0,
             "void_reasons": [{"reason": "metric_unavailable", "count": 1}]}
}
```

`hit_rate_pct = 100 × hit / (hit + miss)`; sem `hit` e sem `miss` → `null`. `n` inclui `void`.
A ordem é métrica ASC e horizonte ASC, não ranking.

## 5. Métricas suportadas

| Métrica | Fonte | Unidade pública | Observado |
|---|---|---|---|
| `iv_atm_30d` | `metrics_underlying.iv_atm_30d` | `% a.a.` | valor gravado |
| `vrp` | `metrics_underlying.vrp` | pontos de vol | valor gravado |
| `rr25` | `metrics_underlying.rr25` | pontos de vol | valor gravado |
| `spot` | `metrics_underlying.spot` ou fechamento `010`/`020` do COTAHIST | R$ | fechamento EOD ÷ 100 |

Métrica desconhecida é rejeitada na API. Horizonte permitido: 1…252 sessões. `evaluate_on` precisa
ser sessão válida e distar exatamente `horizon_sessions` da sessão da decisão, como na F6.

## 6. Lote de avaliação

- `b3o evaluate [--date AAAA-MM-DD]` é o comando manual.
- O `prepare` roda o lote após `metrics` verdes; `prepare-watch` aplica Alembic antes de iniciar e
  repete o ciclo horário. O atalho “nada novo” também verifica previsões pendentes elegíveis.
- O lote avalia no **primeiro pregão real posterior a `evaluate_on`**, mesmo executando vários dias
  depois. Se esse pregão ainda não existe no lake, a previsão continua `pending`.
- Comparação determinística: `<`, `<=`, `>`, `>=`.
- Métrica ausente/indisponível → `void metric_unavailable`, nunca zero ou `miss`.
- Posição fechada não cancela a previsão.
- Lote repetido/concorrente não duplica evento.

## 7. PWA

- `/diario` substitui o placeholder por lista, formulário mobile-first e relatório de calibração.
- `TokenGate`, `Dialog`, tabelas focáveis, métricas/glossário e estados da Carteira são reutilizados.
- Rascunho + `client_decision_id` ficam em `sessionStorage` até sucesso/descarte; token nunca entra
  no rascunho.
- 401 limpa só o token e preserva o rascunho. 409 recarrega lista/detalhe e preserva o rascunho.
- Durante o POST, `Dialog busy` bloqueia Escape/backdrop/cancelar e todos os campos.
- `/api/journal*` é `NetworkOnly` no service worker, antes da rota genérica `/api/`.
- Validação visual: 412 px, alvos ≥ 44 px, zero overflow horizontal e zero erros de console.

## 8. Aceitação

A implementação técnica é validada por smokes e regressões. A aceitação do dono continua pendente
de **30 sessões de pregão consecutivas com decisão real, sem lacuna**, e **≥ 10 previsões distintas
avaliadas automaticamente**. Em 24/11/2026 o dono confirmou que “30 dias” significa sessões de
pregão: cada sessão real precisa de ao menos uma decisão; fim de semana e feriado não contam como
lacuna. Esses dados não são fabricados.
